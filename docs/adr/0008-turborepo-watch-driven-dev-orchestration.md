# Turborepo drives local dev via `turbo watch`, and its task graph now governs build/typecheck ordering

Local dev orchestration was entirely manual: each package's `dev`/`build`/`typecheck` was run by hand, in the right order, from memory. This had a real cost — `web-app` resolves `@fitnest/shared` and `@fitnest/api` through their **built** output (`shared`'s `package.json` `main`/`exports` point at `dist/index.js`/`dist/index.d.ts`, not source), so editing `packages/shared/src` required manually rebuilding `shared` before `web-app`'s dev server or typecheck would see the change. Separately, the root `build`/`typecheck` scripts (`tsc --build` / `tsc --build --noEmit`) silently only covered `shared` and `api` — the root `tsconfig.json`'s `references` array never included `web-app`/`mobile-app`, which use a separate, non-composite tsconfig and resolve workspace packages via npm-workspace symlinks, not TS project references.

We introduced Turborepo, with two decisions worth recording because they're easy to second-guess without this context.

## Considered Options

**Plain `turbo run dev --parallel`** (rejected) would start `api`'s and `web-app`'s dev servers side by side with correct startup ordering, but has no ongoing role afterward — it doesn't react to later file changes. It would not fix the stale-dist problem, which was the actual motivation for adopting Turborepo in the first place (local dev orchestration, not CI — no CI pipeline exists yet).

**`turbo watch dev`** (chosen) is a persistent, dependency-aware process. Because `dev` declares `dependsOn: ["^build"]`, editing a file under `packages/shared/src` makes turbo watch rerun `shared`'s `build`, and because `dev` is also marked `interruptible: true`, turbo watch then kills and restarts the already-running `api`/`web-app` dev processes so they re-resolve the freshly built `@fitnest/shared`. `interruptible: true` is the one non-default flag that makes this real: without it, turbo watch would still rebuild `shared` but leave the stale dev servers running untouched, and the problem would persist unchanged.

**Fixing the TS project-references graph instead** (rejected, for this pass) — extending root `tsconfig.json`'s `references` to include `web-app`/`mobile-app` and adding a `shared`→`api` reference edge would make `tsc --build` cover the full graph. We didn't do this: `web-app`/`mobile-app` use bundler-mode resolution (`moduleResolution: "bundler"`) and aren't composite projects, so wiring them into the reference graph is a separable, more invasive change with its own tradeoffs. Turborepo's task graph — derived from each package's `package.json` workspace `dependencies` (`shared → {api, web-app, mobile-app}`, `api → {web-app, mobile-app}`) — already gives correct build/typecheck ordering without touching tsconfig at all, so we let it supersede TS references as the thing that governs ordering, and left the references graph as-is.

## Consequences

- Root `build`/`typecheck` (`turbo run build` / `turbo run typecheck`) now silently widen from 2 packages to all 4 — `mobile-app`'s `typecheck` output becomes visible in normal repo-wide runs for the first time, even though its implementation is separate, in-progress work. This is intentional, not a regression, but worth knowing if `mobile-app` errors start showing up in `npm run typecheck` output that didn't appear before this change.
- `interruptible` requires Turborepo ≥2.1; the pinned version (`2.10.9`) is well past this, but a future downgrade below that line would silently no-op the flag rather than error, quietly regressing the stale-dist fix back to "rebuild manually."
- The root `tsconfig.json`'s `references` array (`shared`, `api` only) is now purely a `tsc --build`-time convenience for those two packages in isolation — it is no longer the source of truth for cross-package build ordering anywhere in the repo. If it's ever extended to cover `web-app`/`mobile-app`, that's a separate decision, not required by this one.
- Remote caching (Vercel remote cache or self-hosted) was deliberately not set up alongside this — there's no CI yet to benefit from a shared cache. Revisit via `npx turbo login` / `turbo link` once CI exists.
