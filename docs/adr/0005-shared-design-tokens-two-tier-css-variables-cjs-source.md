# Shared design tokens: two-tier, CSS-variable-wired, with a single `.cjs` source of truth

The `@fitnest/shared` design layer models color as a **two-tier token system** — theme-independent **primitives** (raw palette as RGB channel triplets) mapped to **semantic** roles (`primary`, `background`, `foreground`, …) per theme — and wires the semantic layer through **CSS variables** so a single class (`bg-primary`) resolves per theme on both platforms. The **single source of truth is a `.cjs` token module** (`tokens/primitives.cjs`, `tokens/semantic.cjs`); every other artifact (the Tailwind preset's `colors` map, the `:root` variable values injected by the preset's own plugin, and the typed `themes` export) **derives** from it and holds no color values of its own.

The goal driving this is *change-flexibility first, theme-flexibility second* (dark mode is planned but deferred), and *no shared React components* — that remains closed by the earlier no-`react-native-web` decision, so the "design system" is a **shared styling substrate**, not a shared component tree.

## Considered Options

**Token tiers.** Single-tier (`primary = #16a34a`) was rejected: dark mode later would mean rewriting what each role points at, with nowhere clean to express "same role, different value per theme." Two-tier lets a theme swap the *mapping*, not the palette, so `className`s only ever name semantic roles and dark mode becomes additive.

**Theme wiring.** Config-time static resolution (semantic names bake to a literal hex at build) was rejected because it throws away most of the two-tier benefit — a baked semantic token is still one value, so dark mode would force duplicating every utility (`dark:…`) or shipping a second compiled theme. **CSS variables** (`rgb(var(--primary) / <alpha-value>)`, values supplied to `:root`) is the only mechanism where one class resolves per theme and dark mode is a pure add. Cost accepted: colors must be stored as **channel triplets** (`22 163 74`, not hex) so opacity utilities keep working.

**Variable injection — one mechanism for both platforms.** The `:root` variable *values* are injected by a **Tailwind plugin inside the preset** — `plugins: [({ addBase }) => addBase({ ':root': deriveVarsFrom(tokens) })]` — deriving the map from the `.cjs` token module the preset already requires. This is **NativeWind v4's own documented theming pattern** ([Themes guide](https://www.nativewind.dev/docs/guides/themes)): `addBase({ ':root': { '--x': '255 0 0' } })` sets the default theme values, and the same class (`bg-primary`) resolves on web (compiled `@layer base`, SSR-safe) and native (NativeWind processes the base `:root`). Rejected alternatives: hand-writing `:root` in each app's CSS (re-duplicates the values), runtime JS injection (breaks SSR), and a `tsx` codegen step emitting `theme.css` (extra generated artifact) — the preset plugin needs none of them. NativeWind's `vars()` function is **reserved for dynamic, scoped themes** (e.g. a user-chosen brand color applied to a subtree via `style`), not the static base theme, so `App.tsx` needs no manual `vars()` wiring.

**Source-of-truth file format.** This is the surprising one and the reason for this ADR:

- **`.mjs` — rejected.** The preset is a *config-time* file loaded by **two different module systems**: `mobile-app/tailwind.config.js` loads it via `require()` (Metro/NativeWind, CommonJS) and `web-app/tailwind.config.js` via `import` (ESM, `type: module`). `.cjs` is the only extension both can load — `require()` reads it natively and ESM can default-import it. An `.mjs` preset breaks the mobile `require()` path with `ERR_REQUIRE_ESM`. Modernity is not the axis that matters for a Node-loaded config file.
- **`.ts` — rejected for the source of truth.** Runtime consumers (native `vars()`, the `themes` export, the app bundles) handle `.ts` fine, but the config-time preset must `require()` the tokens, and that path won't transpile TS. Keeping tokens as `.ts` would force either a `tsx` codegen step emitting a `.cjs`/JSON artifact, or duplicating the semantic key names into the preset — more moving parts for no authoring benefit.
- **JSON — viable but not chosen.** Dual-consumable, but can't reference a primitive by symbol (`primary: green600`) or carry comments, both of which a palette wants.
- **`.cjs` — chosen.** The only option that is simultaneously `require()`-able at config time, importable by runtime TS (via NodeNext CJS interop; a colocated `tokens.d.cts` supplies types if inference needs it), single-file, and build-step-free.

## Consequences

- In a `"type": "module"` package, a plain `.js` is ESM; the `.cjs` extension on `tokens/*` and `tailwind-preset.cjs` is **deliberate** — it marks the files that must stay `require()`-able from the config-time / Metro side. Do not "modernize" them to `.mjs`/`.ts` without reintroducing a codegen step.
- The Tailwind preset holds **no color values** — only semantic *names* as `var(--…)` references (plus radii/spacing/fontFamily). This is what removes the old preset↔`themes` hex duplication at its root.
- Adding a color is a deliberate act that touches the token module once; the preset, web CSS, native vars, and typed `themes` all derive from it.
- Dark mode later is additive: the preset plugin emits a second override (a `.dark:root` / `prefers-color-scheme` block) from a second semantic map, driven on native by NativeWind's `darkMode: 'class'` + `colorScheme`. No component or class churn, and still one injection mechanism.
- **No React components are shared** across `web-app` and `mobile-app` (the no-`react-native-web` decision stands). The shared boundary is a **styling *contract*** — tokens + `tailwind-variants` class-string functions (`buttonVariants`, …) + their variant-prop *types* — never a component tree. Each platform applies the class strings to its own primitive (`<button>` vs `<Pressable>`); app-local `ui/` wrappers are introduced only on real reuse, and the variant catalogue grows on demand (a second consumer), not speculatively.
- **Tokenized vocabulary:** color (theme-varying → CSS variables) and typography (a named type scale; `fontFamily` slot deferred until a brand font is chosen). Spacing/sizing **inherit Tailwind's defaults** rather than a bespoke scale. All non-color tokens are **static preset values** (no `var()`), since only color is theme-swapped.
- **`tokens/` vs `constants/` seam:** the rule is *"does styling read it?"* → `tokens/` (color, type, radii, and later motion/z-index). `constants/` holds only **non-visual** shared app values (`APP_NAME`, later shared enums/config). This keeps design values from drifting into `constants/` divorced from the token system.
- The typed `themes` export ships **types + a lazy `getThemeColors(theme)`** only (no eager raw-hex map — the old one was unused and was itself a duplication). It graduates to a `useColorScheme`-aware hook when the first imperative color consumer (e.g. `StatusBar` bg) actually appears.
